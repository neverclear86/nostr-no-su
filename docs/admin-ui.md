# 管理 UI

この文書は、管理 UI の画面、アカウントの操作と変更の結果の見え方、リレーの追加・用途の編集・削除、クライアントの接続（`nostrconnect://`）、接続の承認（auth_url フロー）、同梱プラグインのページ、状態を変えるリクエストの守り方を説明する。
起動、認証、待ち受けのアドレスとポート、リバースプロキシーの設定は [設定](configuration.md) の「管理 UI の待ち受けと認証」と「リバースプロキシーの設定」に、環境変数は同じく「環境変数」にある。

## 画面

どのページも上部の左端にロゴを置く。ロゴは製品の図形と製品名「Nostr-no-Su」を並べたもので、全体がダッシュボードへのリンクである。製品名は M PLUS 2 の字形をパスにした SVG で、「Nostr」と「Su」は文字の色、「-no-」は主の色（primary）で描き、ライトとダークのテーマに従う。フォントは配信しない。

ダッシュボードの先頭には、概要の帯（`Overview`）に 5 項目（「承認待ち」（`Pending`）、「アカウント」（`Accounts`）、「セッション」（`Sessions`）、「リレー」（`Relays`）、「プラグイン」（`Plugins`））が区切りの線で分けて並ぶ。各項目はアイコンと見出し、値、補足の語からなり、同じページの節へのリンクになっている（承認待ちが 0 件のときはその節が出ないので、承認待ちの項目だけリンクにならない）。値は件数で、プラグインは「動作中の件数/全件数」の形にし、読み込めなかった候補は数えない。広い画面では 5 列、狭い画面では 2 列で、承認待ちの項目は 2 列のとき全幅を占める。一覧を得られない項目は、値が「—」、補足が「取得できません」（`Not available`）になり、どちらもエラーの色で出る。要対応の補足の語は、その語だけを状態の色とアイコンで出す（「未接続 N」（`N disconnected`）、「応答なし N」（`N unanswered`、`N unavailable`）、「過負荷 N」（`N overloaded`）、「バンカー用が未登録」（`No bunker relay`）は警告の色、「読み込めない行 N」（`N unreadable rows`）、「無効 N」（`N disabled`）、「読み込み失敗 N」（`N failed to load`）はエラーの色）。承認待ちが 1 件以上あるときは、承認待ちの項目を主の色で塗り、補足に「承認を待っています」（`Awaiting your decision`）と「最短 M:SS で失効」（`Soonest expires in M:SS`）を出す。概要の帯の下には、承認待ちが 1 件以上あるとき（または一覧を得られないとき）だけ「承認待ちの接続」（`Pending connections`）の帯が全幅に出る。帯の見出しには、題の横の ⓘ のボタン（「補足を表示」（`Show help`））と件数のピルが付き、ⓘ にマウスを重ねるか、キーボードで移るか、押すと「承認するまで、このクライアントは署名も暗号化も依頼できません。」（`Until you approve, this client cannot request signing or encryption.`）の補足が開く。帯の見出しには、ダッシュボードを自動で読み込み直しているときだけ右に「30 秒ごとに更新」（`Refreshes every 30 s`）が出る。承認待ちは作成の新しい順にカードで並び、広い画面では 2 列になる。カードには、残り時間の円（600 秒が満たんで、中央に「分:秒」。60 秒未満は警告の色）、クライアント pubkey の鍵の指紋と省略した表示（全文は `title` とコピーボタンで得る）、secret の提示の区別のバッジ（「secret 提示なし」（`Secret not offered`）か、警告の色の「secret 不一致」（`Secret mismatch`））、署名者、失効まで（「8:12（12:12:43 に失効）」の形。時刻は閲覧者のローカルの時刻で、JS が動かないときは UTC の表記になる。60 秒未満は警告の記号が付く）、要求された権限（`connect` の perms を 1 つずつチップにし、空なら「権限の要求なし」（`No permissions requested`）のバッジ）、承認・拒否のボタンが並ぶ。secret が一致しないカードは枠が警告の色になり、secret を再生成する前の接続 URI か推測の試みであることを伝える囲みが出て、ボタンは並びを変えずに「拒否する」（`Deny`）が塗り、承認が警告の色の枠の「それでも承認する」（`Approve anyway`）になる。承認待ちが 1 件以上あるときは、ダッシュボードを 30 秒ごとに自動で読み込み直す（ダイアログを開いた状態で返す POST の応答のダッシュボードは読み込み直さない）。署名者は、アカウントの一覧と突き合わせてラベルと省略した npub で出し、一覧に無い署名者と一覧を得られないときは省略した 16 進の pubkey を出す。アカウント（読み込めなかった行は数えない）か、バンカーに使うリレーが 0 件のときは、承認待ちの帯の位置（承認待ちの帯があればその下）に「はじめに」（`Getting started`）の帯が出る。帯には「バンカー用のリレーを追加」（`Add a bunker relay`）、「アカウントを登録」（`Register an account`）、「接続 URI をクライアントに貼る」（`Paste the connection URI into a client`）の 3 段が番号付きで並び、各段に短い説明が付く。済んだ段には「済み」（`Done`）のバッジが付き、まだの最初の 2 段には、追加のダイアログを開く「リレーを追加」（`Add relay`）と「アカウントを追加」（`Add account`）のボタンが付く。3 段目は前の 2 段が済むまで開けないので、点線の枠で操作を置かずに出す。アカウントとリレーのどちらかの一覧を得られないときは、段が済んだかを決められないので帯を出さない。その下は、幅が 1120px を超える画面では左が 1.62、右が 1 の幅の 2 列で、左にアカウント・セッション、右にリレー・プラグインを置き、1120px 以下ではこの順に 1 列で並ぶ。アカウントの節には、見出しに ⓘ（補足は「登録した秘密鍵です。接続 URI をクライアントに貼ると、この鍵で署名します。」）、件数のピル、「DB から読み直す」（`Reload from database`）ボタン、「アカウントを追加」（`Add account`）のボタンが並ぶ。行ごとに、アイコン（公開鍵から決まる 5 × 5 の模様の鍵の指紋。そのアカウントの kind 0 の `picture` が `https:` の画像で、管理者のブラウザーが読めたときは画像を重ねる。JS が動かないときは常に鍵の指紋になる）、大きい太字のラベル、省略した npub（全文は `title` とコピーボタンで得る）、署名者の承認済みセッションの件数（「セッション N 件」（`N sessions`）。セッションの一覧を得られないときは出さない）、「接続 QR コード」（`Connection QR code`）のボタン（狭い画面ではアイコンだけ）が並び、その下に「接続 URI と操作」（`Connection URIs and actions`）の畳みが付く。アイコンの URL は、監視の用途のリレーから取った最新の kind 0 のものである。ダッシュボードを描くときに、前の取得から 5 分を過ぎていれば取り直す。取り直しが 1 秒で終わらないときは、その描画では前に取った URL を使い（初めて取るときは鍵の指紋になる）、結果は次の描画から出る。取得に失敗したときは前に取った URL を使い続け、30 秒の後に取り直す。畳みを開くと、secret 入りの `bunker://` 接続 URI（補足「承認なしで接続できます。自分のクライアントに貼ってください。」）、承認を経る URI（補足「この URI で接続したクライアントは、ダッシュボードの承認待ちで承認するまで署名できません。」）、16 進の公開鍵の 3 つのコピー欄（URI の 2 つの補足は欄の見出しの横の ⓘ で開く）と、「ラベルを編集」（`Edit label`）、「秘密鍵を表示」（`Show private key`）、「secret を再生成」（`Rotate secret`）のダイアログを開くボタン、右端に離した「削除」（`Delete`）のダイアログを開くボタンが出る（16 進の公開鍵はこの中にだけ出る）。「読み込めなかったアカウント」（`Unreadable accounts`）は、起動時の読み込みで飛ばされた行が 1 件以上あるときだけアカウントの節の末尾に出るエラーの色の枠で、題の件数のピル、警告の 1 文と、行ごとに灰色の鍵の指紋・ラベル・省略した npub・理由・「削除」（`Delete`）のダイアログを開くボタンが並ぶ。`pubkey` 列を読めない行は指紋も識別も削除のボタンも出さず、理由の 1 文に「この行は pubkey を読めないため、画面からは削除できません。」（`This row cannot be deleted here because its pubkey cannot be read.`）を続ける。飛ばされた行が 0 件のとき、一覧を得られないときは枠ごと出さない。承認済みのクライアントセッションの節には、見出しの件数のピルと、「クライアントを接続」（`Connect a client`）のボタンが並び、見出しの ⓘ で「クライアントは、ここに出ている権限の範囲で署名と暗号化を依頼できます。」（`Clients can request signing and encryption within the permissions shown here.`）の補足が開く（一覧を得られないときも出る）。行は最終利用の新しい順に並び、広い画面では 1 段目にクライアント pubkey（鍵の指紋、省略した表示とコピーボタン）・署名者・最終利用の相対時刻（「最終利用 たった今」「最終利用 N 分前」「最終利用 N 時間前」「最終利用 N 日前」。`title` に最終利用と作成の UTC の時刻）、2 段目に今の権限のチップと、「権限を編集」（`Edit permissions`）・「承認を取り消す」（`Revoke`）のダイアログを開くボタンを置く。幅 720px 以下では、クライアント、署名者と最終利用、権限のチップ、ボタンの 4 段に組み替える。セッションの署名者も、承認待ちと同じくアカウントの一覧と突き合わせてラベルと省略した npub で出す。リレーの節には、見出しの件数のピルと、「追加」（`Add`）のボタンが並び、見出しの ⓘ で用途の凡例（「監視」（`monitor`）は「登録アカウントのイベントを購読してプラグインに渡す」（`Subscribes to registered accounts' events and passes them to plugins`）、「バンカー」（`bunker`）は「NIP-46 のリクエストを受け付ける」（`Accepts NIP-46 requests`））が開く。行ごとに、1 段目に URL と「用途を編集」（`Edit roles`）と「リレーを削除」（`Delete relay`）のアイコンだけのボタン（語は `aria-label`）が、2 段目に用途 2 つ（監視、バンカー）のマスが並び、マスにはアイコンと語と状態のバッジ（使っていない用途は「未使用」（`Unused`））が入る。プラグインの節には、見出しに件数のピルが並び、行の一覧に有効なプラグインの名前とその状態（「動作中」（`running`）、「過負荷」（`overloaded`）、「無効」（`disabled`）、「応答なし」（`unavailable`））が並ぶ。無効の行には「再有効化」（`Re-enable`）ボタンが付き、押すとダッシュボードへ戻る。ランナーが応答しないときは「変更を確認できませんでした」（503）のページになる。リレーとプラグインの状態は、アイコンと状態の語のバッジで示し、色だけに頼らない。プラグインの破棄の件数と無効の理由は状態のバッジの下に出し、「ページを開く」（`Open`）と「再有効化」（`Re-enable`）のボタンは行の右に置く（狭い画面で収まらなければ下の段に回る）。「読み込めなかったプラグイン」（`Plugins that failed to load`）は、起動時に `PLUGIN_DIR` から読み込めなかった候補が 1 件以上あるときだけプラグインの節の末尾に出るエラーの色の枠で、題の件数のピル、題の下の警告の 1 文（「これらのプラグインは動作していません。下の理由を直してサーバーを再起動してください。」）と、行ごとに「読み込み失敗」（`failed to load`）のバッジ、モジュール名かディレクトリー名、英語のままの理由が並ぶ（理由はログにも同じ文が出る）。プラグインが供給するページ（`/plugins/<プラグイン名>/<ページ>`）の見出しとブラウザーのタブの題は、プラグイン名とページの表示名を「 — 」でつないだもの（例: 「event_logger — Settings」）で、どちらもプラグイン由来の文字列を訳さずに出す（表示の言語を受け取るプラグインでは、ページの表示名はその言語のものになる）このページは、チェックボックス・1 行の文字列の欄・複数行の文字列の欄と送信ボタンからなるフォームを出せる。送信は同じページへ戻り、拒否・呼び出しの失敗は「プラグインの操作に失敗しました」（`Plugin action failed`）になる。アカウント、承認待ち、セッションの節は表示のたびにバンカーへ問い合わせるので、実行中に追加・削除したアカウントもそのまま反映される。読み込み中や DB の障害で一覧を得られないときは、その節に一覧の代わりに理由がエラーの色の囲みで出る（読み込み中は `accounts are being loaded`、DB の障害では `account store unavailable: <理由>`）。承認待ち・アカウント・セッションの 3 つの一覧が同じ理由で得られないときは、概要の帯の直下にエラーの色の囲みを 1 つ出して理由をそこで 1 回だけ出し（日本語では「承認待ち、アカウント、セッションの一覧を表示できません。」を前に置く）、3 つの節には「上の理由で取得できません。」（`Not available for the reason above.`）の 1 文だけを出す。承認待ちの帯は、0 件と読み違えないよう一覧を得られないときも帯ごと出す。アカウントの節はこれに加えて、接続 URI の組み立てに要るリレーの一覧を `relay_list` から得られないとき、`relay list did not answer` を出す。アカウント、セッション、プラグインの節は、行が 0 件のとき、点線の枠の中にアイコンと説明の文を出し、アカウントには「アカウントを追加」（`Add account`）、セッションには「クライアントを接続」（`Connect a client`）の枠のボタンを添える（プラグインは管理 UI から追加できないので、ボタンの代わりに、ディレクトリーに置いたプラグインがサーバーの再起動で読み込まれることを説明の文で出す）。バンカーに使うリレーが無ければ、リレーの節と接続 QR コードのダイアログに、エラーの色の囲みで「バンカーに使うリレーがありません。…」（`No relay is used for the bunker. …`）が出る。リレーの節は、`relay_list` が応答しなければ `relay list did not answer` を、DB を読めなければ DB の理由（`database is unreachable or rejected the connection` など）を、一覧の代わりに出す。承認待ち・アカウント・読み込めなかったアカウント・セッション・リレー・プラグインの 6 つの一覧は、共通の締め切り（5 秒）の下で同時に問い合わせる。「読み込めなかったプラグイン」は起動時に確定した一覧なので、この締め切りの外にある。締め切りまでに間に合わなかったとき、承認待ち・アカウント・セッションの節は、3 つとも間に合わなくても先頭の囲みにはまとめず、それぞれ一覧の代わりに「今は取得できません。」（`Not available right now.`）をエラーの色の囲みで出し、対応する概要の項目の値は「—」、補足は「取得できません」（`Not available`）になる（「読み込めなかったアカウント」の枠は間に合わなくても枠ごと描かない）。リレーとプラグインの節は締め切り超過でも節ごとは潰れず、行を残して状態だけ「応答なし」（`unavailable`）のバッジにする。リレーの一覧自体は締め切りの外で得るが、行ごとの用途（監視、バンカー）の接続状態が締め切りまでに得られないときは、その用途だけがこのバッジになる。

権限のチップは、承認待ちのカード、承認済みのセッションの行、権限の編集のダイアログ（そのほかの宣言）で同じ形である。`perms` のトークンごとに、人の語のあとに生の値（`sign_event:1` など）を等幅で並べる。人の語は、`sign_event` が「すべての kind の署名」（`Sign any kind`）、`sign_event:<kind>`（`<kind>` は 0 以上の整数を符号も 0 埋めも付けずに書いたもの）が kind の名前の署名（0 = 「プロフィール」、1 = 「投稿」、3 = 「フォロー」、6 = 「リポスト」、7 = 「リアクション」、10002 = 「リレーリスト」。表に無い kind は「kind 30023 の署名」（`Sign kind 30023`）のように番号にする）、`nip44_encrypt` が「NIP-44 で暗号化」（`Encrypt with NIP-44`）、`nip44_decrypt` が「NIP-44 で復号」（`Decrypt with NIP-44`）である。バンカーが対応していない権限（`nip04_encrypt`、`nip04_decrypt`）は、点線のチップに「未対応」（`Unsupported`）と生の値を出し、チップの並びの下に「「未対応」の権限は、このバンカーが実装していない方法です。許可しても要求は拒否します。」の 1 行を添える。これら以外の宣言は、生の値だけのチップにする。

アカウントの追加のダイアログは「既存の秘密鍵を登録」（`Import a private key`）と「新しい秘密鍵を生成」（`Generate a new key`）のタブで、登録は主操作のボタン、生成は枠のボタンになる。登録のタブの秘密鍵（nsec）の欄は、貼り付けの説明（登録した後は管理パスワードの再入力でだけ表示すること、ブラウザーに保存させないこと）を、欄の見出しの横の ⓘ のボタン（「補足を表示」（`Show help`））で開く補足に畳む。補足は閉じていても欄の説明として読み上げられ、マウスを重ねるか、キーボードでボタンに移るか、ボタンを押すと開く。生成した鍵のダイアログは省略した npub（全文は `title` とコピーボタンで得る）を、秘密鍵の表示、アカウント 1 件への操作、接続 QR コード、読み込めなかった行の削除のダイアログは、対象のアカウントをラベルと省略した npub（同じくコピーボタン付き）で示す。リレーの追加と用途の編集では、用途（監視、バンカー）をアイコンと語と説明が並ぶ 1 行ずつのチェックで選び、編集のダイアログと画面ではその用途の今の接続状態のバッジも付く。クライアントの接続の署名者の選択欄には、ラベルと省略した npub が並ぶ。結果を伝える通知のページ（「変更を確認できませんでした」、「見つかりません」、400 / 503 など）は、どれもカードの中に結果の印と理由を並べ、ダッシュボードへのリンクを添える形で揃えている。

ダッシュボードのアカウントの追加と、リレーの追加、用途の編集、削除と、アカウントのラベルの編集、秘密鍵の表示、secret の再生成、削除、接続 QR コード、読み込めなかったアカウントの削除は、ページを移らずにダイアログで開く。入力の誤り（400）と、管理パスワードの不一致（403）、書き込まれていないことが確定した失敗（409）は、同じダイアログが理由と送った値（nsec とパスワードを除く）を入れて開いた状態のダッシュボードで返る（下の「クライアントの接続」、「リレーの追加」、「リレーの用途の編集と削除」、「変更の結果」の表）。生成した鍵と秘密鍵の表示も、応答のダッシュボードに開いたダイアログで出し、この 2 つは Esc で閉じない。このダッシュボードは自動で読み込み直さず、開いたダイアログの「キャンセル」と「閉じる」はダッシュボード（`/`）へのリンクで、閉じた後に再読み込みしても送り直さない。ダイアログは「キャンセル」（`Cancel`）か「閉じる」（`Close`）のボタンか Esc キーで閉じ、閉じても何も送らない。「キャンセル」は送信のボタンの右に並ぶ。開いたときは「キャンセル」か「閉じる」にフォーカスが当たる。承認待ちがあってダッシュボードを 30 秒ごとに読み込み直しているときは、開いているダイアログも読み込み直しで閉じ、入力は消える。アカウントの追加のダイアログには「既存の秘密鍵を登録」（`Import a private key`）と「新しい秘密鍵を生成」（`Generate a new key`）のタブが並び、開いたときは登録のタブを選んでいる。タブも JS を使わずに切り替わり、「生成する」（`Generate`）で生成した鍵のダイアログが開く（ラベルはそこで入れる）。セッションの節の「クライアントを接続」（`Connect a client`）と、行ごとの「権限を編集」（`Edit permissions`）と「承認を取り消す」（`Revoke`）も、ダイアログで開く。これらには画面が無く、ダイアログでだけ行う。

画面は日本語と英語で表示する。上部バーの右端の切り替えで選んだ言語は cookie（`nostr_no_su_language`、365 日）に保存し、ページをまたいで保つ。言語の切り替えは、ブラウザーの設定（地球のアイコン）、English、日本語のボタンを 1 つの枠に並べ、表示している言語のボタンを押した状態で示す。「ブラウザーの設定」を押すと cookie を消し、ブラウザーの `Accept-Language` の言語、どちらでもなければ英語で表示する。テーマは上部バーの右端で、ブラウザーの設定（モニター）、ライト（太陽）、ダーク（月）のアイコンのボタンから選び、今のテーマのボタンを押した状態で示す。アイコンだけのボタンの名前は、読み上げとマウスを重ねたときの表示に出す。ライトとダークはどちらも自前の配色で、daisyUI の組み込みのテーマは使わない。どちらのテーマも、文字と地の組み合わせは WCAG 2 の AA のコントラスト比（本文と状態色の文字は 4.5:1、入力とボタンの枠は 3:1）を満たす。文字は OS のフォント（本文はヒラギノ角ゴシック、Noto Sans CJK JP、Yu Gothic UI、メイリオなど、等幅は ui-monospace、SF Mono、Cascadia Mono など）で表示し、Web フォントは読み込まない。上部バーとタブのロゴは、テーマに関係なく同じ色の図形を白い丸い板に載せたもので、README の先頭のロゴと同じ絵である。ライトとダークは cookie（`nostr_no_su_theme`、365 日）に保存し、ブラウザーの設定では cookie を消す。秘密鍵を表示するダイアログ（生成した鍵、秘密鍵の表示）を開いた応答でテーマか言語を切り替えると、ダッシュボードへ戻り、秘密鍵はもう表示されない。Origin と Host が一致しない要求への 400 のページにも、切り替えの POST が同じ不一致で同じ 400 になるので置かない。バンカー、アカウントストア、設定、プラグインから届く理由は英語のまま表示する。プラグインのページのフォームの送信が拒否された、または呼び出しに失敗したときの本文もプラグイン由来の英語のままである。ただし、アカウントの変更とリレーの変更、クライアントの接続、承認・拒否・取り消しで出る「変更を確認できませんでした」（`Change not confirmed`）のページの本文は訳す（プラグインの再有効化で出る同じページの本文は英語のままだが、やり直す前にダッシュボードで確かめるよう促す一文はどちらにも付く）。承認待ちの一覧に無いトークンの承認ページの 404 の本文も訳す。「読み込めなかったアカウント」の枠の理由も、`vault.RowError` の型で届くので訳す。アカウントの登録で公開鍵が登録済みのとき（「このアカウントはすでに登録されています。」（`account is already registered`））と、変更の対象のアカウントが登録されていないとき（一覧に無い署名者の 404 と同じ案内）の理由も、バンカーが型で返すので訳す。設定、DB、プラグインの理由は、ログにも同じ文が出る。

## アカウントの操作

アカウントの行の「接続 QR コード」のボタンと、「接続 URI と操作」の畳みの中の次のボタンから操作する。どれもダッシュボードでダイアログを開き、「接続 QR コード」以外はその中のフォームから `/accounts/<pubkey>/<操作>` へ POST で実行する。このパスは POST だけを受け、ほかのメソッドは 405 になる。

- **「接続 QR コード」（`Connection QR code`）**: ダイアログに、「接続 URI」（`Connection URI`）と「接続 URI（要承認）」（`Connection URI (approval)`）を切り替える 2 つのタブを出す。タブはラジオボタンと CSS で切り替わるので JS は要らず、既定では接続 URI のタブを選ぶ。各タブには 2 通りの QR コードがある。既定に出すのは端末のカメラ用で、`bunker://` を外し `relay=` の値のドットを `%2E` にした形を載せる。完全な `bunker://` URI の QR コードは「クライアントの読み取り機能で読み取る」（`Scan with the client's own scanner`）の畳みの中に入る。接続 URI のタブの先頭には、コードと URI に接続 secret が含まれることの警告を畳まずに出す。要承認の URI のタブには、接続したクライアントがダッシュボードの「承認待ちの接続」で承認されるまで署名できない旨を添える。カメラ用のコードの貼り方の案内は、タブの下に 1 回だけ出す。続けて、この URI が使うバンカーのリレーの URL を出す。QR コードは 288px 四方（幅 375px の画面ではダイアログの幅に合わせて 280px）で、どちらの幅でもダイアログに収まる
- **「ラベルを編集」（`Edit label`）**: ラベルを差し替える。ラベルは空にできず、前後の空白を除いて 100 符号位置以内で、前後を含めて制御文字（Unicode の Cc、行区切りと段落区切り（U+2028、U+2029）、双方向テキストの埋め込み・上書き・分離（U+202A〜U+202E、U+2066〜U+2069））を含められない
- **「秘密鍵を表示」（`Show private key`）**: 管理パスワードを再入力すると、送信の応答のダッシュボードに開いた「秘密鍵」（`Private key`）のダイアログに nsec を表示する（パスワードのダイアログには nsec を含めない）。Basic 認証の資格情報を覚えたブラウザーの前にいる者が、操作 1 回で秘密鍵を表示できないようにするための再入力である
- **「secret を再生成」（`Rotate secret`）**: 接続 secret を作り直す。古い URI での新しい `connect` は承認なしには通らなくなるが、承認済みのセッションは残る。クライアントには新しい URI を貼り直す
- **「削除」（`Delete`）**: バンカーと DB から鍵を消す。その署名者のセッションと承認待ちも消える

「読み込めなかったアカウント」の枠の行の「削除」（`Delete`）も、`pubkey` 列を読めない行を除いてダイアログを開き、同じ `/accounts/<pubkey>/delete` へ POST する。ダイアログの要約はラベルと省略した npub で、説明はその行用（DB からも消えること、nsec を控えていなければ失うこと、以前のマスターキーに戻せば秘密鍵を表示して控えられること）になる。

アカウントの追加、生成した鍵、ラベルの編集のダイアログのラベルの欄の下には、上限の 1 行（「100 文字まで（絵文字は数文字分になることがあります）。」（`Up to 100 characters (an emoji can count as several).`））が出る。生成した鍵のバックアップの警告、秘密鍵のダイアログの再送の注意、削除のダイアログの説明、入力の誤りは、畳まずに常に出す。

## クライアントの接続（`nostrconnect://`）

セッションの節の見出しの「クライアントを接続」（`Connect a client`）で開くダイアログで接続する。セッションが 0 件のときは、節の中の同じボタンからも開ける。クライアントが出した `nostrconnect://` URI を欄に貼り付け、ラベルと省略した npub で並ぶ一覧から署名するアカウントを選んで「確認へ進む」（`Review`）を押すと、接続の前に確認のダイアログが開く。URI の欄の下には「nostrconnect:// で始まる URI。」の補足が出る。URI のリレーは `relays` テーブルに登録せず、開いたセッションが持つ。「接続する」を押すと、バンカーは基本のバンカーリレー（`relays` テーブルでバンカーの用途を持つリレー）に無い URI のリレーへセッションのリレーとして接続し、どれかが応答の発行先になるまで最大 15 秒待ってからセッションを開いて `connect` の応答を出す。セッションのリレーには、そのリレーを持つセッションの署名者の `#p` の購読と AUTH（NIP-42）と、それらのセッションのクライアントへの応答だけが届く。基本のバンカーリレーには、全署名者の `#p` の購読と全アカウントの AUTH と、すべてのクライアントへの応答が届く。承認の取り消し、`logout`、アカウントの削除などでセッションが無くなり、ほかのセッションも使わなくなったセッションのリレーの接続は閉じる。セッションのリレーは管理 UI のリレーの一覧には出ない。アカウントが 0 件のときはフォームの代わりに登録への案内を、一覧を得られないときは理由をダイアログに出す。URI を解釈できないときと署名者が一覧に無いときは 400 で、接続のダイアログを開いた状態でダッシュボードを返し、先頭に理由を出して貼った URI と選んだアカウントを戻す。アカウントの一覧を得られないときは 503 で、同じダイアログを開いた状態で返し、フォームの代わりに理由を出す。

確認のダイアログ（「接続の内容を確認」（`Review the connection`））は、URI を解釈して署名者を確かめた後に、開いた状態のダッシュボードで返り、この時点ではセッションもリレーの接続も作らない。名乗る名前（URI の `name`。無ければ行を出さず、制御文字を除き、100 符号位置を超えるぶんは切って末尾を `…` にする）、クライアント公開鍵（省略とコピーボタン）、署名者、要求された権限のチップ、URI のリレー（URI に現れた順に 1 行ずつ、省略しない）を並べ、接続の意味の説明を出す。権限が空のときは、許す操作の一文を説明に続ける。「接続する」（`Connect`）を押すと `/sessions/connect/confirm` へ URI と署名者を送り直し、サーバーはもう一度解釈と照合をしてから接続する。「キャンセル」（`Cancel`）はダッシュボードへ戻る。接続の段で失敗したとき（URI のリレーに繋がらない 503、バンカーが受け付けない 409 と 503）は、同じ確認のダイアログを開いた状態で返し、先頭に理由を出す。

承認済みのセッションの行の「権限を編集」（`Edit permissions`）で開くダイアログで、そのセッションの `perms` を書き換えられる。ダイアログは行ごとにあり、そのセッションの今の権限を入れて開く。フォームには署名（`sign_event`）・NIP-44 の暗号化（`nip44_encrypt`）・復号（`nip44_decrypt`）を許すかの 3 つのチェックと、署名を許可しないときだけ使う kind の欄（カンマ区切り）が並ぶ。kind の欄の使い方は、見出しの横の ⓘ のボタン（「補足を表示」（`Show help`））で開く補足に出る。補足は閉じていても欄の説明として読み上げられ、マウスを重ねるか、キーボードでボタンに移るか、ボタンを押すと開く。kind 24133 を常に拒否する注意は、署名のチェックの下に畳まずに出す。このフォームが扱わない宣言（`connect` で送られた未知のトークン、負の kind や `sign_event:01` のような 0 埋めの kind の署名など）は、そのほかの宣言として読み取り専用のチップで示し、保存の値の末尾にそのまま残す。このフォームからはすべての操作を拒否する設定はできず、そうしたいときは「承認を取り消す」（`Revoke`）を使う。保存の結果は、入力の誤りが 400、書き込まれていないことが確定したときが 409 で、どちらも同じダイアログを開いた状態でダッシュボードを返し、先頭に理由を出して送った欄の状態を戻す。バンカーが受け付けられないとき・反映されたか分からないとき・セッションの一覧を得られないときは 503 の通知ページで、成功は 303 でダッシュボードへ戻す。

行の「承認を取り消す」（`Revoke`）は、クライアントと署名者と取り消しの結果の説明を出す確認のダイアログを開く。ダイアログの中の「承認を取り消す」を押すと `POST /sessions/revoke` へ送り、成功すればダッシュボードへ戻る（303）。

## リレーの追加

リレーの節の見出しの「追加」（`Add`）か、「はじめに」の帯の「リレーを追加」（`Add relay`）で開くダイアログから登録する。フォームは `/relays/new` へ POST する。URL の欄には `ws://` か `wss://` で始まりホストを含む URL を、前後の空白を除いて保存する（貼り付けで混ざりやすい前後の空白だけを除き、末尾の `/` や大文字と小文字は変えない）。用途（監視、バンカー）は、アイコンと語と用途の説明が並ぶ 1 行ずつのチェックで選ぶ。フォームの上には NIP-46 専用のリレーをバンカーにだけ使うよう促す 1 行が、URL の欄の下には「ws:// か wss:// で始まる URL。」の補足が出る。既定ではバンカーだけにチェックが入っており、少なくとも一方を選ぶ必要がある。登録すると DB に書き込んでから接続を開くので、再起動しなくても反映される。

送信の結果は次のように見える。

| 結果 | 画面 | 状態コード |
| --- | --- | --- |
| 反映された | ダッシュボードへ戻る | 303 |
| URL の規則に外れる、用途を 1 つも選んでいない | ダイアログが開き直し、その先頭に理由が出る | 400 |
| 同じ URL がすでに登録済み | ダイアログが開き直し、その先頭に理由が出る | 409 |
| 書き込まれていないことが確定したほかの DB の失敗 | ダイアログが開き直し、その先頭に英語の理由が出る（日本語のページでは「リレーを登録できませんでした。」の前置きが付く） | 409 |
| DB には書けたが確かめられなかった（書き込みの確定、または `relay_list` の反映） | 「変更を確認できませんでした」（`Change not confirmed`）のページ | 202 |

## リレーの用途の編集と削除

各行の「用途を編集」（`Edit roles`）と「リレーを削除」（`Delete relay`）はダイアログを開き、フォームは `/relays/<id>/edit` と `/relays/<id>/delete` へ POST する。`<id>` は DB の行の id で、URL は変えられない（別の URL に変えるときは、追加してから削除する）。編集で変えられるのは用途（監視、バンカー）だけで、両方を外した送信は保存しない。編集のダイアログの用途の行には、その用途の今の接続状態のバッジが付く。編集と削除のダイアログでは、バンカーの用途を外す（削除ではバンカーに使っていた）とそのリレーだけで接続しているクライアントが応答を受け取れなくなることの説明を、フォームの上に畳まずに出す。削除は確認のダイアログを経てから実行する。どちらも DB に書いてから接続を変えるので、再起動しなくても反映される。

結果は次のように見える。

| 結果 | 画面 | 状態コード |
| --- | --- | --- |
| 反映された | ダッシュボードへ戻る | 303 |
| id が整数でない | 「見つかりません」（`Not found`）のページ（この URL にページは無いという案内） | 404 |
| 一覧に無い id（削除済みなど） | 「見つかりません」（`Not found`）のページ（このリレーは登録されていないという案内） | 404 |
| DB の一覧を得られない、開き直すダイアログを描くためのリレーの一覧を得られない、またはその一覧にリレーが無い | 「リレーを利用できません」（`Relays are not available`）のページ | 503 |
| 用途を 1 つも選んでいない（編集のみ） | ダイアログが開き直し、その先頭に理由が出る | 400 |
| 書き込まれていないことが確定したほかの DB の失敗 | ダイアログが開き直し、その先頭に英語の理由が出る（日本語のページでは、編集は「用途を保存できませんでした。」、削除は「リレーを削除できませんでした。」の前置きが付く） | 409 |
| DB には書けたが確かめられなかった（書き込みの確定、または `relay_list` の反映） | 「変更を確認できませんでした」（`Change not confirmed`）のページ | 202 |

## 変更の結果

変更の結果は次のように見える。

| 結果 | 画面 | 状態コード |
| --- | --- | --- |
| 反映された | ダッシュボードへ戻る | 303 |
| 反映されていない（登録済み） | 開き直したダイアログに理由が出る（「このアカウントはすでに登録されています。」） | 409 |
| 反映されていない（書き込まれていないことが確定した DB の失敗） | 開き直したダイアログに英語の理由が出る（日本語のページでは「登録できませんでした。」などの操作ごとの前置きが付く） | 409 |
| アカウントの一覧にも読み込めなかったアカウントの一覧にも無い署名者への操作（削除済みの署名者への削除・secret の作り直し・ラベルの編集、`pubkey` 列を読めない行への削除、管理 UI が一覧を引いてからバンカーが変更を処理するまでの間に削除された場合（同時に送られた削除など）） | 「見つかりません」（`Not found`）のページ（アカウントが登録されていないという案内） | 404 |
| 管理パスワードの再入力が一致しない（秘密鍵の表示） | 1 秒の遅延の後、開き直したダイアログに理由が出る | 403 |
| 受け付けられない（起動時の読み込みか、結果が曖昧な書き込みの後の読み直し、または管理 UI からの読み直しの前、DB の障害で一覧を得られない） | 「アカウントを利用できません」（`Accounts are not available`）のページ（開き直すダイアログの行が一覧から消えていたときも同じ。生成した鍵の登録では、生成した鍵のダイアログに理由が出る） | 503 |
| 反映されたか分からない（書き込みの期限切れ、途中の切断、DB のクライアントの例外、バンカーの無応答） | 「変更を確認できませんでした」（`Change not confirmed`）のページ（生成した鍵の登録では、生成した鍵のダイアログに理由が出る） | 202 |
| 読み直しの POST、受け付けた（読み込み中も含む） | ダッシュボードへ戻る | 303 |
| 読み直しの POST、バンカーが応答しない | 「バンカーを利用できません」（`Bunker is not available`）のページ | 503 |

通知のページ（「見つかりません」（`Not found`）、「変更を確認できませんでした」（`Change not confirmed`）、「承認しました」（`Approved`）など）は、見出しの下のカードに結果の印と理由を並べる。印の色とアイコンはダッシュボードの状態のチップと同じ語彙から取り、反映された（承認）は成功の色の丸のチェック、良し悪しを伝えない（拒否）は色の無い丸のマイナス、反映されたか分からないか今は受け付けられない（202、503）は警告の色の時計、処理できなかった（400、404、405、409）はエラーの色の八角形の警告にする。

「変更を確認できませんでした」（`Change not confirmed`）のページでは、再読み込みで POST を再送せず、ダッシュボードを開いて反映されたかを確かめること。生成した鍵の登録では通知ページにならず、生成した鍵のダイアログで秘密鍵をバックアップしてから「この鍵を登録する」を押し直す。再送した場合の結果は次のとおりで、どの場合も同じ鍵のアカウントが 2 つ登録されることはない。読み直しが終わる前の再送はどれも 503 になる。

| 再送する POST | 最初の変更が反映されていた場合 | 反映されていなかった場合 |
| --- | --- | --- |
| nsec 入力による登録 | 409 「このアカウントはすでに登録されています。」（`account is already registered`。nsec は表示しない） | 登録してダッシュボードへ戻る |
| 生成した鍵の登録 | 409 「このアカウントはすでに登録されています。」（`account is already registered`） | 登録してダッシュボードへ戻る |
| secret の作り直し | secret をもう一度作り直してダッシュボードへ戻る（ダッシュボードは常に最新の URI を出す） | 作り直してダッシュボードへ戻る |
| 削除 | 404 の「見つかりません」（`Not found`）のページ（アカウントはすでに一覧に無い） | 削除してダッシュボードへ戻る |
| ラベルの編集 | 同じラベルで差し替えてダッシュボードへ戻る（害は無い） | 差し替えてダッシュボードへ戻る |

生成の応答を再読み込みすると、別の鍵のダイアログが出るだけで何も登録されない。生成した鍵の登録でラベルが規則に反した場合（400）と、バンカーが登録に失敗した場合（409 / 503 / 202）は、生成した鍵を失わないよう、同じ鍵のダイアログが理由付きで開く。この応答を再読み込みすると登録の POST が再送され、結果は上の表の「生成した鍵の登録」の行のとおりになる。

## 接続の承認（auth_url フロー）

secret を持たない `bunker://` URI（ダッシュボードの「接続 URI（要承認）」（`Connection URI (approval)`）の欄）で接続すると、バンカーはその場では承認せず、NIP-46 の `auth_url` 応答で承認ページの URL をクライアントへ返す。クライアントはその URL をブラウザーで開き、管理 UI にログインして内容（署名者・クライアント pubkey・失効までの時間・secret の提示の区別・要求された権限）を確認したうえで承認または拒否する。承認ページにはこれに加えて、承認するとこのクライアントが上の権限の範囲で署名と暗号化を依頼できること、承認したときの権限を後から「権限を編集」で変えられることの説明が、カードの下に畳まずに情報の色の囲みで出る（権限が空のときは「要求なし。kind 24133 を除く署名と、NIP-44 の暗号化・復号を許します。」（`None requested. Signing any kind but 24133, and NIP-44 encryption and decryption, are allowed.`）が同じ囲みに続く）。承認するとバンカーは元のリクエストと同じ id で `ack` を返し、待っていたクライアントの接続が完了する。拒否するとエラーを返す。承認ページは 30 秒ごとに自動で読み込み直し、その間に失効するか処理済みになると、失効した可能性を含めて訳した本文の 404 の通知ページに変わる。承認ページは枠（iframe）の中では開けないので、クライアントは新しいウィンドウかブラウザーで開く必要がある。承認ページの内容は、ダッシュボードの「承認待ちの接続」（`Pending connections`）と同じカード（残り時間の円、鍵の指紋、secret の提示の区別、署名者、失効まで、権限のチップ、承認・拒否のボタン）で出る。提示された secret が一致しなかった要求では、カードの枠が警告の色になり、secret を再生成する前の URI を使い続けているクライアントか推測の試みであるという説明が警告の色の囲みで出て、ボタンは「拒否する」（`Deny`）が塗り、承認が「それでも承認する」（`Approve anyway`）になる。

承認ページの URL は `ADMIN_BASE_URL` を土台に `<base>/approve/<token>` として組み立てる（既定は `http://localhost:<ADMIN_PORT>`）。クライアントのブラウザーから開ける URL である必要があるため、リバースプロキシーの背後に置くときや別のホストから使うときは公開 URL を設定すること。管理 UI を無効（`ADMIN_PORT=`。同梱の compose では [設定](configuration.md) の「docker compose の構成」の override）にすると承認フローも無効になり、secret の一致しない `connect` は従来どおり `invalid secret` で拒否する。

承認される前にクライアントが再読み込みして `connect` を送り直した場合、承認待ちは最新の要求に置き換わる（同じクライアントの保留が並ばないようにするため）。先に受け取った `auth_url` のページは 404 になるので、新しく開かれた方の承認ページを使う。

承認待ちはダッシュボードの「承認待ちの接続」（`Pending connections`）からも承認・拒否でき、10 分で失効する。承認待ちは全体で 16 件までで、超えると新しい要求と同じクライアントの古い要求から先に（無ければ全体で作成の古い順に）押し出され、押し出された要求の承認ページは 404 になる。承認待ちと承認済みのセッションは DB に保存され、本体を再起動しても残る。承認待ちの失効までの時間は、再起動の前から続く。一度承認したクライアントは、以後 secret 無しで `connect` し直しても承認を求められない。セッションの権限は（署名者, クライアント）の組を最初に承認したときの値のままで、再 `connect` では変わらない。権限を変えるには「承認済みのセッション」（`Approved sessions`）の「権限を編集」（`Edit permissions`）から書き換える。書き換えは次のリクエストから効き、クライアントは接続し直さなくてよい。すべて拒否したいときは「承認を取り消す」（`Revoke`）を使う。ただし、承認済みのセッションが上限（全体で 32 件）を超えると最終利用の古い順に押し出され、押し出されたクライアントは再び承認を求められる（取り消すには「承認済みのセッション」（`Approved sessions`）の「承認を取り消す」（`Revoke`）を使う）。取り消すとダッシュボードへ戻る。

承認・拒否・取り消しが成功しなかったときの見出しと状態コードは次のとおりで、いずれもダッシュボードへのリンクを出す。

| 結果 | 見出し | 状態コード | 次の行動 |
| --- | --- | --- | --- |
| 対象が無い（不明、失効、上限で押し出された、処理済み、承認済みでない組） | 「見つかりません」（`Not found`） | 404 | やり直さない（ダッシュボードで状態を確かめる） |
| 書き込まれていないことが確定した | 「変更を反映できませんでした」（`Change not applied`） | 409 | やり直してよい |
| 受け付けられない（読み込み・読み直しの前） | 「バンカーを利用できません」（`Bunker is not available`） | 503 | 時間をおいてやり直す |
| 承認待ちの一覧を得られない（承認ページの GET、承認・拒否の POST） | 「バンカーを利用できません」（`Bunker is not available`） | 503 | 時間をおいて開き直す |
| 反映されたか分からない | 「変更を確認できませんでした」（`Change not confirmed`） | 503 | ダッシュボードで反映されたかを確かめてからやり直す |

クライアントがログアウト（`logout`）しても DB に書けなかったとき（ログに `failed to close the session of` の行が出る）は、「承認済みのセッション」（`Approved sessions`）に行が残るので、「承認を取り消す」（`Revoke`）で消す。承認・拒否・取り消しの結果が「変更を確認できませんでした」（`Change not confirmed`）のページになったときは、ダッシュボードで結果を確かめる。承認は「承認済みのセッション」（`Approved sessions`）にその組があるかを確かめ、あればクライアントから接続し直す（承認は求められない）。無ければ「承認待ちの接続」（`Pending connections`）から承認し直す。取り消しは「承認済みのセッション」（`Approved sessions`）に組が残っていれば取り消し直す。拒否は「承認待ちの接続」（`Pending connections`）に要求が残っていれば拒否し直す。

## 同梱プラグインのページ

同梱のプラグインのページは、ダッシュボードのプラグインの節のそのプラグインの行から開く。`event_logger` のページ（「タイムライン」（`Timeline`）と「設定」（`Settings`））は [使い方](usage.md) の「イベントを保存する（event_logger）」にある。

`profile` のページ「プロフィール」（`Profile`、`/plugins/profile/profile`）は、登録アカウントごとの節に、npub、今のプロフィール（kind 0）の作成時刻（「更新日時」（`updated`））、`picture` と `banner` の画像、8 項目を編集するフォームを出す。欄のラベルは表示の言語の項目名（「名前」（`Name`）など）で、欄の下に kind 0 のキー名（`name`、`display_name`、`about`、`picture`、`banner`、`nip05`、`website`、`lud16`）が出る。出る内容は監視の用途のリレーから取った最新の kind 0 で、最大 60 秒前に取得したものである。フォームを「保存する」（`Save`）で送ると、送る直前に kind 0 を取り直して 8 項目だけを差し替え（未知のキーは残し、空欄の項目はキーごと消す）、そのアカウントの名義で署名して監視の用途のリレーへ送る。kind 0 が見つからないアカウントには空欄のフォームを出す。取得に失敗したアカウントの節には理由だけを出し、フォームを出さない。画像は管理者のブラウザーが画像のホストから直接読み込む（`http:` の画像は次の節の CSP の例外で読む）。仕様の全文は [profile の README](../plugins-src/profile/README.md) にある。

## 状態を変えるリクエストと枠への埋め込み

GET と HEAD 以外のリクエストは、ルーティングの前ですべて `Origin`（無ければ `Referer`）のホストとポートを `Host` と突き合わせて CSRF を防いでいる（ルートごとの検査ではない）。この検査が防御になるのは、ブラウザーが GET と HEAD 以外のリクエストに必ず `Origin` を付けるからである（別のサイトのフォームから送らせた POST には、そのサイトのオリジンが入る）。`Origin` も `Referer` も送らないクライアント（curl など）はブラウザーではなく、他のサイトに送らされることが無いので、そのまま通す。このとき cookie は取り除かれるが、管理 UI の cookie は表示の言語とテーマだけで、認証は Basic 認証の `Authorization` ヘッダーで行うので、cookie の除去は CSRF の防御にはならない（言語とテーマがブラウザーの設定になるだけである）。前段にリバースプロキシーを置くときの `Host` の渡し方は、[設定](configuration.md) の「リバースプロキシーの設定」にある。`Host`、`Origin`、`Referer` のどれかに制御文字を含むリクエストは、メソッドによらずこの検査の前に text/plain の 400（`Bad request`）で弾く。ブラウザーはこれらのヘッダーに制御文字を送らず、検査が不一致のときにログへ出す生の値に端末の制御を入れさせないためである。

認証済みの応答にはすべて `cache-control: no-store`、枠への埋め込みを禁じる `x-frame-options: DENY`、`content-security-policy`、`x-content-type-options: nosniff`、`referrer-policy: same-origin` を付けている。どのページも secret か秘密鍵を含みうるためと、削除やローテーションのダイアログを他のサイトの枠に読み込んでボタンを押させる操作（枠の中の POST は同じオリジンから送られるので CSRF の検査では防げない）を防ぐためである。CSP（`default-src 'none'; script-src 'self'; style-src 'self'; img-src data: https:; form-action 'self'; base-uri 'none'; frame-ancestors 'none'`）は、管理 UI が配信するファイルのスクリプトだけを実行させ、HTML に何かが注入されてもインラインのスクリプトとイベント属性を実行させない。`referrer-policy` を `no-referrer` にしないのは、ブラウザーが同じオリジンへの POST の `Origin` を `null` にし、CSRF の検査がすべての POST を 400 にするためである。上部バーとタブ（favicon）に出すロゴは配信するファイルではなくページに埋め込んだ `data:` の SVG で、`img-src data:` がこれを読ませる。`https:` は、アカウントのアイコンを管理者のブラウザーが画像のホストから直接読むためのもので、Nostr-no-Su は画像を中継しない。プラグインのページの GET の応答だけは `http:` も足して `img-src data: https: http:` にしており、プラグインのページの記述が指す遠隔の画像を管理者のブラウザーが直接取りに行く（[プラグイン API](plugin-api.md) の第 13.4 節）。
