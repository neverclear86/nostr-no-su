# 管理 UI

この文書は、管理 UI の画面、アカウントの操作と変更の結果の見え方、リレーの追加・用途の編集・削除、クライアントの接続（`nostrconnect://`）、接続の承認（auth_url フロー）、状態を変えるリクエストの守り方を説明する。
起動、認証、待ち受けのアドレスとポート、リバースプロキシーの設定は [設定](configuration.md) の「管理 UI の待ち受けと認証」と「リバースプロキシーの設定」に、環境変数は同じく「環境変数」にある。

## 画面

どのページも上部の左端にロゴを置く。ロゴは製品の図形、製品名「Nostr-no-Su」、副題「管理画面」（`Admin`）を並べたもので、全体がダッシュボードへのリンクである。製品名は M PLUS 2 の字形をパスにした SVG で、「Nostr」と「Su」は文字の色、「-no-」は主の色（primary）で描き、ライトとダークのテーマに従う。フォントは配信しない。

ダッシュボードの先頭には 5 枚のタイル（「承認待ち」（`Pending`）、「アカウント」（`Accounts`）、「セッション」（`Sessions`）、「リレー」（`Relays`）、「プラグイン」（`Plugins`））が並び、それぞれ件数と補足の 1 行を出して、同じページの節へのリンクになっている（承認待ちが 0 件のときはその節が出ないので、承認待ちのタイルだけリンクにならない）。承認待ちが 1 件以上あるときは、承認待ちのタイルが警告の色になり、狭い画面では全幅を占める。読み込めなかったプラグインが 1 件以上あるときは、プラグインのタイルが警告の色になり、補足がその件数（「読み込み失敗 N」（`N failed to load`））になる。値の「動作中 / 全件数」には読み込めなかった候補を数えない。タイルの下には、承認待ちが 1 件以上あるとき（または一覧を得られないとき）だけ「承認待ちの接続」（`Pending connections`）の節が警告の色の枠で全幅に出る。承認待ちの行には、クライアント pubkey（先頭と末尾だけを出し、全文は `title` とコピーボタンで得る）、secret の提示の区別のバッジ（「secret 提示なし」（`Secret not offered`）か、警告の色の「secret 不一致」（`Secret mismatch`））、失効までの秒数（60 秒未満は警告の色）、署名者、要求された権限（`connect` の perms を 1 つずつチップにし、空なら「権限の要求なし」（`No permissions requested`）のバッジ）、承認・拒否のボタンが並び、作成の新しい順に出る。承認待ちが 1 件以上あるときは、ダッシュボードを 30 秒ごとに自動で読み込み直す。署名者は、アカウントの一覧と突き合わせてラベルと省略した npub で出し、一覧に無い署名者と一覧を得られないときは省略した 16 進の pubkey を出す。承認待ちの下は、広い画面では 2 列で、左にアカウント・読み込めなかったアカウント・セッション、右にリレー・プラグイン・読み込めなかったプラグインを置き、狭い画面ではこの順に 1 列で並ぶ。アカウントの節には、見出しに件数のピルと「追加」（`Add`）のリンクと「DB から読み直す」（`Reload from database`）ボタンが並び、行ごとにラベル・省略した npub（全文は `title` とコピーボタンで得る）・「接続 URI と公開鍵」（`Connection URIs and public key`）の畳み・アイコン付きの操作のボタン（「接続 QR コード」（`Connection QR code`）、「ラベルを編集」（`Edit label`）、「秘密鍵を表示」（`Show private key`）、「secret を再生成」（`Rotate secret`）、「削除」（`Delete`））が並ぶ。畳みを開くと、secret 入りの `bunker://` 接続 URI、承認を経る URI、16 進の公開鍵の 3 つのコピー欄が出る（16 進の公開鍵はこの中にだけ出る）。「読み込めなかったアカウント」（`Unreadable accounts`）は、起動時の読み込みで飛ばされた行が 1 件以上あるときだけ出るカードで、見出しの件数のピル、警告の 1 文と、行ごとにラベル・省略した npub・理由・「削除」（`Delete`）のボタンが並ぶ。`pubkey` 列を読めない行は識別も削除のリンクも出さず、理由の 1 文に「この行は pubkey を読めないため、画面からは削除できません。」（`This row cannot be deleted here because its pubkey cannot be read.`）を続ける。飛ばされた行が 0 件のとき、一覧を得られないときはカードごと出さない。承認済みのクライアントセッションの節には、見出しの件数のピルと「クライアントを接続」（`Connect a client`）のリンクが並び、行ごとにクライアント pubkey（省略とコピーボタン）・署名者・今の権限のチップ・最終利用の相対時刻（「たった今」「N 分前」「N 時間前」「N 日前」。`title` に最終利用と作成の UTC の時刻）・「権限を編集」（`Edit permissions`）と「承認を取り消す」（`Revoke`）のボタンが、最終利用の新しい順に並ぶ。セッションの署名者も、承認待ちと同じくアカウントの一覧と突き合わせてラベルと省略した npub で出す。リレーの節には、見出しの件数のピルと「追加」（`Add`）のリンクが並び、行ごとに URL、用途 2 つ（監視、バンカー）のアイコンと語と状態のバッジ（使っていない用途は「未使用」（`Unused`））、「用途を編集」（`Edit roles`）と「リレーを削除」（`Delete relay`）のアイコンだけのボタン（語は `aria-label`）が並ぶ。プラグインの節には、有効なプラグインとその状態（「動作中」（`running`）、「過負荷」（`overloaded`）、「無効」（`disabled`）、「応答なし」（`unavailable`））が並ぶ。無効の行には「再有効化」（`Re-enable`）ボタンが付き、押すとダッシュボードへ戻る。ランナーが応答しないときは「変更を確認できませんでした」（503）のページになる。リレーとプラグインの状態は、アイコンと状態の語のバッジで示し、色だけに頼らない。プラグインの破棄の件数と無効の理由は状態のバッジの下に出し、「再有効化」（`Re-enable`）のボタンは行の右に置く。「読み込めなかったプラグイン」（`Plugins that failed to load`）は、起動時に `PLUGIN_DIR` から読み込めなかった候補が 1 件以上あるときだけプラグインの節の下に出るカードで、見出しの件数のピル、警告の 1 文（「これらのプラグインは動作していません。下の理由を直してサーバーを再起動してください。」）と、行ごとにモジュール名かディレクトリー名と英語のままの理由が並ぶ（理由はログにも同じ文が出る）。プラグインが供給するページは、チェックボックス・1 行の文字列の欄・複数行の文字列の欄と送信ボタンからなるフォームを出せる。送信は同じページへ戻り、拒否・呼び出しの失敗は「プラグインの操作に失敗しました」（`Plugin action failed`）になる。アカウント、承認待ち、セッションの節は表示のたびにバンカーへ問い合わせるので、実行中に追加・削除したアカウントもそのまま反映される。読み込み中や DB の障害で一覧を得られないときは、その節に一覧の代わりに理由が出る（読み込み中は `accounts are being loaded`、DB の障害では `account store unavailable: <理由>`）。承認待ちの節ではこの理由をエラーの色の囲みで出し、0 件と読み違えないよう節ごと出す。アカウントの節はこれに加えて、接続 URI の組み立てに要るリレーの一覧を `relay_list` から得られないとき、`relay list did not answer` を出す。バンカーに使うリレーが無ければリレーの節に警告が出る。リレーの節は、`relay_list` が応答しなければ `relay list did not answer` を、DB を読めなければ DB の理由（`database is unreachable or rejected the connection` など）を、一覧の代わりに出す。承認待ち・アカウント・読み込めなかったアカウント・セッション・リレー・プラグインの 6 つの節は、共通の締め切り（5 秒）の下で同時に問い合わせる。「読み込めなかったプラグイン」は起動時に確定した一覧なので、この締め切りの外にある。締め切りまでに間に合わなかったとき、承認待ち・アカウント・セッションの節は一覧の代わりに「今は取得できません。」（`Not available right now.`）を出し、対応するタイルの値は「—」、補足は「取得できません」（`Not available`）になる（「読み込めなかったアカウント」のカードは間に合わなくてもカードごと描かない）。リレーとプラグインの節は締め切り超過でも節ごとは潰れず、行を残して状態だけ「応答なし」（`unavailable`）のバッジにする。リレーの一覧自体は締め切りの外で得るが、行ごとの用途（監視、バンカー）の接続状態が締め切りまでに得られないときは、その用途だけがこのバッジになる。

アカウントの追加（`/accounts/new`）は「既存の秘密鍵を登録」（`Import a private key`）と「新しい秘密鍵を生成」（`Generate a new key`）の 2 枚のカードで、それぞれ見出しにアイコンが付き、登録は主操作のボタン、生成は既定のボタンになる。生成した鍵の確認のページは省略した npub（全文は `title` とコピーボタンで得る）を、登録の完了と秘密鍵の表示、アカウント 1 件への操作の確認のページ、読み込めなかった行の削除の確認のページは、対象のアカウントをラベルと省略した npub（同じくコピーボタン付き）で示す。リレーの追加と用途の編集では、用途（監視、バンカー）をアイコンと語と説明が並ぶ 1 行ずつのチェックで選び、編集の画面ではその用途の今の接続状態のバッジも付く。クライアントの接続の署名者の選択欄には、ラベルと省略した npub が並ぶ。結果を伝える通知のページ（「変更を確認できませんでした」、「見つかりません」、400 / 503 など）は、どれもカードの中に囲みを 1 つ置き、ダッシュボードへのリンクを添える形で揃えている。

画面は日本語と英語で表示する。ナビゲーションバーの右端の切り替えで選んだ言語は cookie（`nostr_no_su_language`、365 日）に保存し、ページをまたいで保つ。言語の切り替えは、ブラウザーの設定（地球のアイコン）、English、日本語のボタンを 1 つの枠に並べ、表示している言語のボタンを押した状態で示す。「ブラウザーの設定」を押すと cookie を消し、ブラウザーの `Accept-Language` の言語、どちらでもなければ英語で表示する。テーマはナビゲーションバーの右端で、ブラウザーの設定（モニター）、ライト（太陽）、ダーク（月）のアイコンのボタンから選び、今のテーマのボタンを押した状態で示す。アイコンだけのボタンの名前は、読み上げとマウスを重ねたときの表示に出す。ライトとダークはどちらも自前の配色で、daisyUI の組み込みのテーマは使わない。どちらのテーマも、文字と地の組み合わせは WCAG 2 の AA のコントラスト比（本文と状態色の文字は 4.5:1、入力とボタンの枠は 3:1）を満たす。文字は OS のフォント（本文はヒラギノ角ゴシック、Noto Sans CJK JP、Yu Gothic UI、メイリオなど、等幅は ui-monospace、SF Mono、Cascadia Mono など）で表示し、Web フォントは読み込まない。上部バーとタブのロゴは、テーマに関係なく同じ色の図形を白い丸い板に載せたもので、README の先頭のロゴと同じ絵である。ライトとダークは cookie（`nostr_no_su_theme`、365 日）に保存し、ブラウザーの設定では cookie を消す。秘密鍵を表示するページ（生成した鍵の確認、登録の完了、秘密鍵の表示）には、押すと表示を失うのでテーマと言語のどちらの切り替えも置かない。Origin と Host が一致しない要求への 400 のページにも、切り替えの POST が同じ不一致で同じ 400 になるので置かない。バンカー、アカウントストア、設定、プラグインから届く理由は英語のまま表示する。プラグインのページのフォームの送信が拒否された、または呼び出しに失敗したときの本文もプラグイン由来の英語のままである。ただし、アカウントの変更とリレーの変更、クライアントの接続、承認・拒否・取り消しで出る「変更を確認できませんでした」（`Change not confirmed`）のページの本文は訳す（プラグインの再有効化で出る同じページの本文は英語のままだが、やり直す前にダッシュボードで確かめるよう促す一文はどちらにも付く）。承認待ちの一覧に無いトークンの承認ページの 404 の本文も訳す。「読み込めなかったアカウント」のカードの理由も、`vault.RowError` の型で届くので訳す。アカウントの登録で公開鍵が登録済みのとき（「このアカウントはすでに登録されています。」（`account is already registered`））と、変更の対象のアカウントが登録されていないとき（一覧に無い署名者の 404 と同じ案内）の理由も、バンカーが型で返すので訳す。設定、DB、プラグインの理由は、ログにも同じ文が出る。

## アカウントの操作

アカウントごとに並ぶ次のボタンから操作する。「接続 QR コード」以外はどれも確認のページを経て POST で実行する。

- **「接続 QR コード」（`Connection QR code`）**: 接続 URI と接続 URI（要承認）を、1 件につき 2 通りの QR コードで出す。既定に出すのは端末のカメラ用で、`bunker://` を外し `relay=` の値のドットを `%2E` にした形を載せる。完全な `bunker://` URI の QR コードは「クライアントの読み取り機能で読み取る」（`Scan with the client's own scanner`）の畳みの中に入る。要承認の URI のカードには、接続したクライアントがダッシュボードの「承認待ちの接続」で承認されるまで署名できない旨と、その節へのリンクを添える。続けて、この URI が使うバンカーのリレーの URL と、クライアント側の `nostrconnect://` で接続する経路への案内を出す。POST は受け付けない
- **「ラベルを編集」（`Edit label`）**: ラベルを差し替える。ラベルは空にできず、前後の空白を除いて 100 符号位置以内で、前後を含めて制御文字（Unicode の Cc）を含められない
- **「秘密鍵を表示」（`Show private key`）**: 管理パスワードを再入力すると nsec を表示する。Basic 認証の資格情報を覚えたブラウザーの前にいる者が、操作 1 回で秘密鍵を表示できないようにするための再入力である
- **「secret を再生成」（`Rotate secret`）**: 接続 secret を作り直す。古い URI での新しい `connect` は承認なしには通らなくなるが、承認済みのセッションは残る。クライアントには新しい URI を貼り直す
- **「削除」（`Delete`）**: バンカーと DB から鍵を消す。その署名者のセッションと承認待ちも消える

「読み込めなかったアカウント」のカードの行の「削除」（`Delete`）も、`pubkey` 列を読めない行を除いて同じ `/accounts/<pubkey>/delete` の確認ページを経る。要約にはラベルと省略した npub に加えて理由が並び、説明はその行用（DB からも消えること、nsec を控えていなければ失うこと、以前のマスターキーに戻せば秘密鍵を表示して控えられること）になる。

## クライアントの接続（`nostrconnect://`）

セッションの節の見出しの「クライアントを接続」（`Connect a client`）から、`/sessions/connect` の画面を開く。クライアントが出した `nostrconnect://` URI を欄に貼り付け、ラベルと省略した npub で並ぶ一覧から署名するアカウントを選んで送信する。URI のリレーはバンカーの用途で登録される（すでに登録済みなら用途を足すだけで、監視の用途は変えない）。アカウントが 0 件のときはフォームの代わりに登録への案内を、一覧を得られないときは理由を出す。

承認済みのセッションの行の「権限を編集」（`Edit permissions`）からは、`/sessions/<signer>/<client>/permissions` の画面でそのセッションの `perms` を書き換えられる。フォームには署名（`sign_event`）・NIP-44 の暗号化（`nip44_encrypt`）・復号（`nip44_decrypt`）を許すかの 3 つのチェックと、署名を許可しないときだけ使う kind の欄（カンマ区切り）が並ぶ。このフォームが扱わない宣言（`connect` で送られた未知のトークンなど）は、そのほかの宣言として読み取り専用のチップで示し、保存の値の末尾にそのまま残す。この画面からはすべての操作を拒否する設定はできず、そうしたいときは「承認を取り消す」（`Revoke`）を使う。保存の結果は、入力の誤りが 400、書き込まれていないことが確定したときが 409、バンカーが受け付けられないとき・反映されたか分からないとき・セッションの一覧を得られないときが 503 で、成功は 303 でダッシュボードへ戻す。

送信の結果は次のように見える。

| 結果 | 画面 | 状態コード |
| --- | --- | --- |
| 反映された | ダッシュボードへ戻る | 303 |
| URI を解釈できない（`nostrconnect://` で始まらない、クライアント公開鍵が不正、クエリーを読めない、リレーが無いか `ws://` / `wss://` でない、`secret` が無い） | フォームに理由が出る | 400 |
| 送った署名者がアカウントの一覧に無い | フォームに理由が出る | 400 |
| URI のリレーが同時に登録されていた | フォームに理由が出る | 409 |
| 書き込まれていないことが確定したほかの DB の失敗（リレーの登録、セッションの記録） | フォームに英語の理由が出る（日本語のページでは「接続を開始できませんでした。」の前置きが付く） | 409 |
| 上限まで待っても URI のリレーのどれにも接続できなかった | フォームに理由が出る | 503 |
| セッションを受け付けられない（読み込み・読み直しの前） | フォームに英語の理由が出る（日本語のページでは前置きが付く） | 503 |
| DB には書けたが確かめられなかった（リレーの登録、書き込みの確定、`relay_list` の反映）、セッションを開けたか確かめられなかった | 「変更を確認できませんでした」（`Change not confirmed`）のページ | 202 |

## リレーの追加

リレーの節の見出しの「追加」（`Add`）から、`/relays/new` の画面で登録する。URL の欄には `ws://` か `wss://` で始まりホストを含む URL を、前後の空白を除いて保存する（貼り付けで混ざりやすい前後の空白だけを除き、末尾の `/` や大文字と小文字は変えない）。用途（監視、バンカー）は、アイコンと語と用途の説明が並ぶ 1 行ずつのチェックで選ぶ。既定ではバンカーだけにチェックが入っており、少なくとも一方を選ぶ必要がある。登録すると DB に書き込んでから接続を開くので、再起動しなくても反映される。

送信の結果は次のように見える。

| 結果 | 画面 | 状態コード |
| --- | --- | --- |
| 反映された | ダッシュボードへ戻る | 303 |
| URL の規則に外れる、用途を 1 つも選んでいない | フォームに理由が出る | 400 |
| 同じ URL がすでに登録済み | フォームに理由が出る | 409 |
| 書き込まれていないことが確定したほかの DB の失敗 | フォームに英語の理由が出る（日本語のページでは「リレーを登録できませんでした。」の前置きが付く） | 409 |
| DB には書けたが確かめられなかった（書き込みの確定、または `relay_list` の反映） | 「変更を確認できませんでした」（`Change not confirmed`）のページ | 202 |

## リレーの用途の編集と削除

各行の「用途を編集」（`Edit roles`）と「リレーを削除」（`Delete relay`）から、`/relays/<id>/edit` と `/relays/<id>/delete` の画面を開く。`<id>` は DB の行の id で、URL は変えられない（別の URL に変えるときは、追加してから削除する）。編集で変えられるのは用途（監視、バンカー）だけで、両方を外した送信は保存しない。編集の画面の用途の行には、その用途の今の接続状態のバッジが付く（接続の状態を得られないときは付かない）。編集の画面には「削除」（`Delete`）のボタンも置く。削除は確認のページを経てから実行する。どちらも DB に書いてから接続を変えるので、再起動しなくても反映される。

結果は次のように見える。

| 結果 | 画面 | 状態コード |
| --- | --- | --- |
| 反映された | ダッシュボードへ戻る | 303 |
| id が整数でない | 「見つかりません」（`Not found`）のページ（この URL にページは無いという案内） | 404 |
| 一覧に無い id（削除済みなど） | 「見つかりません」（`Not found`）のページ（このリレーは登録されていないという案内） | 404 |
| DB の一覧を得られない | 「リレーを利用できません」（`Relays are not available`）のページ | 503 |
| 用途を 1 つも選んでいない（編集のみ） | フォームに理由が出る | 400 |
| 書き込まれていないことが確定したほかの DB の失敗 | フォームに英語の理由が出る（日本語のページでは、編集は「用途を保存できませんでした。」、削除は「リレーを削除できませんでした。」の前置きが付く） | 409 |
| DB には書けたが確かめられなかった（書き込みの確定、または `relay_list` の反映） | 「変更を確認できませんでした」（`Change not confirmed`）のページ | 202 |

## 変更の結果

変更の結果は次のように見える。

| 結果 | 画面 | 状態コード |
| --- | --- | --- |
| 反映された | ダッシュボードへ戻る（nsec 入力による登録だけは完了ページ） | 303（nsec 入力による登録は 200） |
| 反映されていない（登録済み、管理 UI が一覧を引いてからバンカーが変更を処理するまでの間に削除された（同時に送られた削除など）） | フォームに理由が出る（登録済みは「このアカウントはすでに登録されています。」、削除された場合は一覧に無い署名者の 404 と同じ案内） | 409 |
| 反映されていない（書き込まれていないことが確定した DB の失敗） | フォームに英語の理由が出る（日本語のページでは「登録できませんでした。」などの操作ごとの前置きが付く） | 409 |
| アカウントの一覧にも読み込めなかったアカウントの一覧にも無い署名者への操作（削除済みの署名者への削除・secret の作り直し・ラベルの編集、`pubkey` 列を読めない行への削除など） | 「見つかりません」（`Not found`）のページ（アカウントが登録されていないという案内） | 404 |
| 読み込めなかったアカウントの行への削除の GET（`pubkey` 列を読める行に限る） | その行用の削除の確認ページ | 200 |
| 管理パスワードの再入力が一致しない（秘密鍵の表示） | 1 秒の遅延の後、フォームに理由が出る | 403 |
| 受け付けられない（起動時の読み込みか、結果が曖昧な書き込みの後の読み直し、または管理 UI からの読み直しの前、DB の障害で一覧を得られない） | 「アカウントを利用できません」（`Accounts are not available`）のページ（生成した鍵の登録では、生成した鍵の確認ページに理由が出る） | 503 |
| 反映されたか分からない（書き込みの期限切れ、途中の切断、DB のクライアントの例外、バンカーの無応答） | 「変更を確認できませんでした」（`Change not confirmed`）のページ（生成した鍵の登録では、生成した鍵の確認ページに理由が出る） | 202 |
| 読み直しの POST、受け付けた（読み込み中も含む） | ダッシュボードへ戻る | 303 |
| 読み直しの POST、バンカーが応答しない | 「バンカーを利用できません」（`Bunker is not available`）のページ | 503 |

「変更を確認できませんでした」（`Change not confirmed`）のページでは、再読み込みで POST を再送せず、ダッシュボードを開いて反映されたかを確かめること。生成した鍵の登録では通知ページにならず、確認ページで秘密鍵をバックアップしてから「この鍵を登録する」を押し直す。再送した場合の結果は次のとおりで、どの場合も同じ鍵のアカウントが 2 つ登録されることはない。読み直しが終わる前の再送はどれも 503 になる。

| 再送する POST | 最初の変更が反映されていた場合 | 反映されていなかった場合 |
| --- | --- | --- |
| nsec 入力による登録 | 409 「このアカウントはすでに登録されています。」（`account is already registered`。nsec は表示しない） | 登録して完了ページ（nsec を表示） |
| 生成した鍵の登録 | 409 「このアカウントはすでに登録されています。」（`account is already registered`） | 登録してダッシュボードへ戻る |
| secret の作り直し | secret をもう一度作り直してダッシュボードへ戻る（ダッシュボードは常に最新の URI を出す） | 作り直してダッシュボードへ戻る |
| 削除 | 404 の「見つかりません」（`Not found`）のページ（アカウントはすでに一覧に無い） | 削除してダッシュボードへ戻る |
| ラベルの編集 | 同じラベルで差し替えてダッシュボードへ戻る（害は無い） | 差し替えてダッシュボードへ戻る |

nsec 入力による登録の完了ページを再読み込みすると、同じ nsec の再送は 409 になり、nsec は再び表示されない。生成の確認ページを再読み込みすると、別の鍵の確認ページが出るだけで何も登録されない。生成した鍵の登録でラベルが規則に反した場合（400）と、バンカーが登録に失敗した場合（409 / 503 / 202）は、生成した鍵を失わないよう、同じ鍵の確認ページが理由付きで出る。この確認ページを再読み込みすると登録の POST が再送され、結果は上の表の「生成した鍵の登録」の行のとおりになる。

## 接続の承認（auth_url フロー）

secret を持たない `bunker://` URI（ダッシュボードの「接続 URI（要承認）」（`Connection URI (approval)`）の欄）で接続すると、バンカーはその場では承認せず、NIP-46 の `auth_url` 応答で承認ページの URL をクライアントへ返す。クライアントはその URL をブラウザーで開き、管理 UI にログインして内容（署名者・クライアント pubkey・失効までの時間・secret の提示の区別・要求された権限）をダッシュボードの承認待ちの行と同じ体裁で確認したうえで承認または拒否する。承認ページにはこれに加えて、承認するとこのクライアントが上の権限の範囲で署名と暗号化を依頼できること、承認したときの権限を後から「権限を編集」で変えられることの説明が情報の色の囲みで出る（権限が空のときは「要求なし。kind 24133 を除く署名と、NIP-44 の暗号化・復号を許します。」（`None requested. Signing any kind but 24133, and NIP-44 encryption and decryption, are allowed.`）が同じ囲みに続く）。承認するとバンカーは元のリクエストと同じ id で `ack` を返し、待っていたクライアントの接続が完了する。拒否するとエラーを返す。承認ページは 30 秒ごとに自動で読み込み直し、その間に失効するか処理済みになると、失効した可能性を含めて訳した本文の 404 の通知ページに変わる。承認ページは枠（iframe）の中では開けないので、クライアントは新しいウィンドウかブラウザーで開く必要がある。提示された secret が一致しなかった要求の承認ページには、先頭に「接続 secret が一致しません。」（`The connection secret does not match.`）の警告と、secret を再生成する前の URI を使い続けているクライアントか推測の試みであるという説明が出る。ダッシュボードの行には出ない。

承認ページの URL は `ADMIN_BASE_URL` を土台に `<base>/approve/<token>` として組み立てる（既定は `http://localhost:<ADMIN_PORT>`）。クライアントのブラウザーから開ける URL である必要があるため、リバースプロキシーの背後に置くときや別のホストから使うときは公開 URL を設定すること。管理 UI を無効（`ADMIN_PORT=`）にすると承認フローも無効になり、secret の一致しない `connect` は従来どおり `invalid secret` で拒否する。

承認される前にクライアントが再読み込みして `connect` を送り直した場合、承認待ちは最新の要求に置き換わる（同じクライアントの保留が並ばないようにするため）。先に受け取った `auth_url` のページは 404 になるので、新しく開かれた方の承認ページを使う。

承認待ちはダッシュボードの「承認待ちの接続」（`Pending connections`）からも承認・拒否でき、10 分で失効する。承認待ちは全体で 16 件までで、超えると新しい要求と同じクライアントの古い要求から先に（無ければ全体で作成の古い順に）押し出され、押し出された要求の承認ページは 404 になる。承認待ちと承認済みのセッションは DB に保存され、本体を再起動しても残る。承認待ちの失効までの時間は、再起動の前から続く。一度承認したクライアントは、以後 secret 無しで `connect` し直しても承認を求められない。セッションの権限は（署名者, クライアント）の組を最初に承認したときの値のままで、再 `connect` では変わらない。権限を変えるには「承認済みのセッション」（`Approved sessions`）の「権限を編集」（`Edit permissions`）から書き換える。書き換えは次のリクエストから効き、クライアントは接続し直さなくてよい。すべて拒否したいときは「承認を取り消す」（`Revoke`）を使う。ただし、承認済みのセッションが上限（全体で 32 件）を超えると最終利用の古い順に押し出され、押し出されたクライアントは再び承認を求められる（取り消すには「承認済みのセッション」（`Approved sessions`）の「承認を取り消す」（`Revoke`）を使う）。取り消すとダッシュボードへ戻る。

承認・拒否・取り消しが成功しなかったときの見出しと状態コードは次のとおりで、いずれもダッシュボードへのリンクを出す。

| 結果 | 見出し | 状態コード | 次の行動 |
| --- | --- | --- | --- |
| 対象が無い（不明、失効、上限で押し出された、処理済み、承認済みでない組） | 「見つかりません」（`Not found`） | 404 | やり直さない（ダッシュボードで状態を確かめる） |
| 書き込まれていないことが確定した | 「変更を反映できませんでした」（`Change not applied`） | 409 | やり直してよい |
| 受け付けられない（読み込み・読み直しの前） | 「バンカーを利用できません」（`Bunker is not available`） | 503 | 時間をおいてやり直す |
| 承認待ちの一覧を得られない（承認ページの GET、承認・拒否の POST） | 「バンカーを利用できません」（`Bunker is not available`） | 503 | 時間をおいて開き直す |
| 反映されたか分からない | 「変更を確認できませんでした」（`Change not confirmed`） | 503 | ダッシュボードで反映されたかを確かめてからやり直す |

クライアントがログアウト（`logout`）しても DB に書けなかったとき（ログに `failed to close the session of` の行が出る）は、「承認済みのセッション」（`Approved sessions`）に行が残るので、「承認を取り消す」（`Revoke`）で消す。承認・拒否・取り消しの結果が「変更を確認できませんでした」（`Change not confirmed`）のページになったときは、ダッシュボードで結果を確かめる。承認は「承認済みのセッション」（`Approved sessions`）にその組があるかを確かめ、あればクライアントから接続し直す（承認は求められない）。無ければ「承認待ちの接続」（`Pending connections`）から承認し直す。取り消しは「承認済みのセッション」（`Approved sessions`）に組が残っていれば取り消し直す。拒否は「承認待ちの接続」（`Pending connections`）に要求が残っていれば拒否し直す。

## 状態を変えるリクエストと枠への埋め込み

GET と HEAD 以外のリクエストは、ルーティングの前ですべて `Origin`（無ければ `Referer`）のホストとポートを `Host` と突き合わせて CSRF を防いでいる（ルートごとの検査ではない）。この検査が防御になるのは、ブラウザーが GET と HEAD 以外のリクエストに必ず `Origin` を付けるからである（別のサイトのフォームから送らせた POST には、そのサイトのオリジンが入る）。`Origin` も `Referer` も送らないクライアント（curl など）はブラウザーではなく、他のサイトに送らされることが無いので、そのまま通す。このとき cookie は取り除かれるが、管理 UI の cookie は表示の言語とテーマだけで、認証は Basic 認証の `Authorization` ヘッダーで行うので、cookie の除去は CSRF の防御にはならない（言語とテーマがブラウザーの設定になるだけである）。前段にリバースプロキシーを置くときの `Host` の渡し方は、[設定](configuration.md) の「リバースプロキシーの設定」にある。`Host`、`Origin`、`Referer` のどれかに制御文字を含むリクエストは、メソッドによらずこの検査の前に text/plain の 400（`Bad request`）で弾く。ブラウザーはこれらのヘッダーに制御文字を送らず、検査が不一致のときにログへ出す生の値に端末の制御を入れさせないためである。

認証済みの応答にはすべて `cache-control: no-store`、枠への埋め込みを禁じる `x-frame-options: DENY`、`content-security-policy`、`x-content-type-options: nosniff`、`referrer-policy: same-origin` を付けている。どのページも secret か秘密鍵を含みうるためと、削除やローテーションの確認ページを他のサイトの枠に読み込んでボタンを押させる操作（枠の中の POST は同じオリジンから送られるので CSRF の検査では防げない）を防ぐためである。CSP（`default-src 'none'; script-src 'self'; style-src 'self'; img-src data:; form-action 'self'; base-uri 'none'; frame-ancestors 'none'`）は、管理 UI が配信するファイルのスクリプトだけを実行させ、HTML に何かが注入されてもインラインのスクリプトとイベント属性を実行させない。`referrer-policy` を `no-referrer` にしないのは、ブラウザーが同じオリジンへの POST の `Origin` を `null` にし、CSRF の検査がすべての POST を 400 にするためである。上部バーとタブ（favicon）に出すロゴは配信するファイルではなくページに埋め込んだ `data:` の SVG で、`img-src data:` がこれを読ませる。プラグインのページの GET の応答だけは `img-src data: https: http:` にしており、プラグインのページの記述が指す遠隔の画像を管理者のブラウザーが直接取りに行く（[プラグイン API](plugin-api.md) の第 13.4 節）。
