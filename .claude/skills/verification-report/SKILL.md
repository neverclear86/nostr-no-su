# 動作確認レポート（nostr-no-su）

対象のリポジトリは `neverclear86/nostr-no-su`（private）である。
レポートの手本は #45 と #54 で、どちらも issue 本文に概要を、最初のコメントに詳細レポートを置いている（最初のレポートは #16）。
#54 は管理 UI の刷新（#29）の後のレポートで、日本語の画面を撮り、表示の言語や画面の幅の確認を含む。
作業を始める前に直近のレポートを読み、構成を合わせる。

```sh
gh issue view 54 -R neverclear86/nostr-no-su
gh api repos/neverclear86/nostr-no-su/issues/54/comments --jq '.[0].body'
```

コマンドの具体例は同じディレクトリの [reference.md](reference.md) にまとめてある。

## 守ること

- **スクリーンショットの貼り方**：`gh` の `--attach` で添付する（gh 2.100 以上）。画像を置くためのブランチやリポジトリ内のファイルは作らない。ブラウザーからのアップロードもしない
- **ユーザーの環境**：ユーザーが動かしている compose スタック（コンテナー名 `nostr-no-su-*`、127.0.0.1:8080）と作業ツリーは使わず、止めもしない。検証はスクラッチパッドに `git worktree add` した main から、プロジェクト名 `nns-verify` と空いているポートで行う
- **鍵とパスワード**：使い捨ての秘密鍵、マスターキー、管理パスワードだけを使い、スクラッチパッドに置く。レポートにも使い捨てであることを書く
- **文体**：issue とコメントは標準的な技術文体の日本語で書く。書く前に `japanese-tech-writing` スキルを読む
- **不具合の扱い**：コードは直さない。見つけた不具合は別 issue として起票し、レポートから参照する（#16 と #17、#45 と #46 の前例）
- **エージェント**：作業をエージェントに任せるときは opus を使う

## 手順

### 1. 対象を決める

`git log --oneline -1 origin/main` で対象のコミットを決める。
README、`docs/admin-ui.md`、`docs/architecture.md`、直近の issue と PR を読み、前回のレポート以降に増えた機能を確認項目に足す。
環境を立てる前に、ユーザーの `nostr-no-su-*` コンテナーの状態を記録しておく。
ユーザーのスタックは動いていないこともあるので、後片付けではこの記録と同じ状態であることを確かめる。

### 2. 環境を立てる

compose は worktree の `docker-compose.yml` に、strfry 2 台を足す override ファイルを重ねて起動する。
環境変数は `--env-file` でスクラッチパッドから渡し、worktree には置かない。
毎回同じ引数になるので、ラッパーのスクリプトにしておく。

- strfry のイメージは既定の設定で 127.0.0.1 に bind するので、そのままでは他のコンテナーから届かない。`bind = "0.0.0.0"` に書き換えた設定ファイルをマウントする
- `ADMIN_PORT` はアプリの待ち受けとホストへの公開の両方に効く。`ADMIN_BASE_URL` も同じポートで設定すると、`auth_url` をホストのブラウザーでそのまま開ける
- `event_logger` プラグインは本体と同じ gleam イメージの中でビルドし、worktree の `plugins/event_logger` に出力する。出力は root 所有になるので、`chmod -R a+rX` もコンテナーの中で行う
- 起動の順序は、Postgres と strfry、プラグインのビルド、本体のイメージのビルド、本体の順にする
- `gleam test` は worktree で、使い捨ての Postgres を `TEST_DATABASE_URL` に渡して実行し、件数を検証環境の節に書く。`build` は `.dockerignore` で除かれるので、本体のイメージのビルドと並行してよい

### 3. 検証する

各項目で実際の出力（ログ、状態コード、クライアントの出力）を保存し、レポートにはそこから抜粋する。
compose を env を変えて作り直すと前のコンテナーのログが消えるので、作り直す前に `logs` を保存する。

1. **起動**：healthy、非 root、再起動回数 0、`schema ready` と `loaded N account(s)`。全行が時刻と水準で始まる。マスターキーが無いときと不正なときに、`[main] cannot start: <理由>` の 1 行だけを出して終了コード 1 で終了し、`restart: unless-stopped` により再起動を繰り返すこと
2. **管理 UI のアカウント管理**：Playwright で実際のブラウザーを操作し、状態コードとヘッダーは curl でも確かめる。nsec 入力による登録、重複（409）と不正な nsec（400、入力値を表示しない）、鍵の生成（確認ページだけに nsec、登録は 303）、生成した鍵のラベル不正（途中に制御文字を置く。同じ nsec の確認ページを再表示）、ラベルの編集（絵文字を含む）と 101 文字のラベル（400）、コピーのボタン、秘密鍵の再表示（誤ったパスワードで 403、正しいパスワードで 200 とログ 1 行）、削除（再送は 404）、secret のローテーション
3. **NIP-46 とバンカー経由の投稿**：UI からコピーした URI で、connect、get_public_key、sign_event、ping、nip44_encrypt、nip44_decrypt、logout を実行する。kind 1 を署名して 2 台のリレーへ発行し、読み戻して署名を検証する
4. **再起動なしのアカウント変更**：クライアントを接続したまま UI でアカウントを追加し、すぐ署名できること、削除すると応答しなくなること、既存のセッションが続くことを確かめる
5. **ローテーション**：古い URI からの新しい connect は承認待ち（`auth_url`）になり、接続済みのセッションは続く。残った承認待ちは拒否して片付ける
6. **永続化**：本体のコンテナーを再起動しても同じ URI で署名できること。`pg_dump` に平文の鍵も secret も無いこと
7. **DB の停止と復帰**：`docker pause` で止め、署名と監視が続くこと、最初の変更が 202 になり以後の操作が 503 になること、ログが再試行のたびには出ず、理由が変わったときだけ出ることを確かめる（アカウントストアの `unavailable` の行は、読み直しの期限切れと接続の確保の失敗で 2 行になることがある）。その行の `retrying in` の値は 5000ms から失敗のたびに倍に延び、2 分で頭打ちになる。`docker unpause` の後の復帰は次の再試行まで（最長 2 分）待つので、`account store is back` がすぐに出なくても不具合ではない
8. **マルチリレーと重複排除**：2 台から同じイベントが届いても `events` は 1 行で、kind 24133 は保存されないこと
9. **auth_url と取り消し**：secret 無しの URI で接続して承認と拒否を行い、承認済みセッションを取り消す。承認済みセッションは本体の再起動で消えるので、項目 6 の直後に行うと、セッションの少ないダッシュボードを撮れる
10. **管理 UI の保護**：未認証の 401、`/healthz`、未知のパスの 404、誤ったメソッドの 405、別オリジンの POST の 400、アカウントのページの `cache-control: no-store` と枠への埋め込みの禁止
11. **管理 UI の表示**：CSS（`/static/admin.css`）が認証の後で配信され、worktree の `priv/static/admin.css` と同じであること、ブラウザーの要求先が管理 UI のオリジンだけであることを確かめる。表示の言語が cookie、`Accept-Language`、英語の順に決まること、`POST /language` が 303 と `Secure` の無い `set-cookie` を返し、戻り先が別のオリジンを指さないこと、`Origin` も `Referer` も無い POST では cookie が使われないこと、秘密鍵を表示する 3 ページ（登録の完了、生成した鍵の確認、秘密鍵の表示）に切り替えが無いことを確かめる。幅 1280 と 375 で横にはみ出さないこと（`scrollWidth`）、ダークテーマ、コピーの完了表示、JS を無効にしたときのフォームの送信も確かめる
12. **リレー**：`docker restart` で片方を再起動して再接続と購読の再開を確かめ、`docker stop` で片方を止めた状態で署名と投稿が成立することを確かめる
13. **スーパービジョン**：`nns.env`（環境の節）の `REMSH_ENABLED=true` で開いた remsh の口に、`./dc.sh exec -T nostr-no-su /app/start.sh remsh` で式を流し、バンカーのアクター（登録名が `nostr_no_su_bunker$` で始まる）を kill する。コマンド例は reference.md の「アクターの kill（remsh）」を見る。式の出力の `restarted=true`（同じ名前で別の pid）、ログの `error Supervisor: ... Context: child_terminated. Reason: killed.` の 1 行、続く `[bunker] loaded N account(s)`（DB からの読み直し）、`./dc.sh ps` で本体のコンテナーが再起動されていないこと（Up の時間が続く）、接続したままのクライアントで `sign` が続くことを確かめる。Supervisor の `error` の行は kill による期待どおりの出力で、OTP のクラッシュレポートも error の行として同じ形で出る（README の「docker compose」の節）ので、項目 1 の「全行が時刻と水準で始まる」も崩さない。remsh には `q().` と `init:stop().` を送らない（本体が止まる）
14. **署名者 0 件**：アカウントをすべて削除すると購読が閉じ、追加すると戻ることを確かめる。アカウントが無くなるので、撮影をすべて終えてから最後に行う
15. **秘密の grep**：全ログと `pg_dump` を、秘密鍵（16 進と nsec）、secret、マスターキー、管理パスワード、DB のパスワードで検索し、一致が 0 件であることを確かめる。応答本文は、鍵を表示するページを除き、secret 以外の値で検索する（ダッシュボードは secret 入りの URI を表示する仕様である）。`ERROR` の行が出たとき（grep の失敗、`targets.txt` が読めないか空、行の形の崩れ）は、原因を直して検索し直す

### 4. スクリーンショットを撮る

Playwright で幅 1280、ページ全体を撮る。
ブラウザーのコンテキストに `locale: "ja-JP"` を渡し、日本語の画面で撮る（渡さないと Chromium は `Accept-Language` に `en-US` を送り、英語の画面になる）。
表示の言語は cookie が `Accept-Language` より優先されるので、英語に切り替えたコンテキストで撮り続けると英語の画面になる。
英語の画面を撮った後は、日本語に切り替え直すか、新しいコンテキストで撮る。
ファイル名の番号はレポート本文での並び順にする。
同じ名前で撮り直すと前の画面が消えるので、再実行のときは撮らないか名前を変える。
承認済みセッションはクライアントを終了しても残るので、ダッシュボードの撮影はセッションが増える前に行うか、不要なセッションを取り消してから行う。
ボタンを押した後の同じページで撮ると、マウスが残ったボタンにホバーの色が付くので、`page.mouse.move(0, 0)` でマウスを外すか、新しいコンテキストで開いて撮る。

### 5. 投稿する

1. レポートの issue を作る。本文は目的、検証環境、確認項目（結果に合わせてチェックする）、結果の順に書く
2. 不具合があれば別 issue として起票する。レポートの issue と不具合の issue は互いに番号を参照するので、先にレポートの issue を仮の文字列入りで作り、不具合の issue を作ってから `gh issue edit` で差し替える
3. 詳細レポートをコメントとして投稿する。画像は本文で `![代替テキスト](./04-dashboard-accounts.png)` のようにローカルのパスで参照し、スクリーンショットのディレクトリで同じパスを `--attach` に渡す。gh が参照を `https://github.com/user-attachments/assets/...` に書き換える。#54 では 30 枚を 1 つのコメントに添付できた
4. 投稿後に本文を取得し、`./` の参照が残っていないこと、画像の数が添付した数と一致すること、各 URL が認証付きで `200 image/png` を返すことを確かめる

詳細レポートの構成は #54 に合わせる。
対象コミット、検証環境の表、結果サマリーの表、領域ごとの節（ログの抜粋と、UI の節にはスクリーンショット）、気づいた点、後片付けの順である。

### 6. 後片付け

- `nns-verify` のスタックを volume とビルドしたイメージごと消し、バックグラウンドのプロセスも止める。strfry、`postgres:17-alpine`、gleam のイメージはほかの作業でも使うので消さない
- worktree の root 所有のファイルをコンテナー経由で消してから、`git worktree remove --force` で worktree を消す
- ユーザーの `nostr-no-su-*` コンテナーが手順 1 の記録と同じ状態であること（動いていたコンテナーは再起動されずに動いていること）を確かめる
- スクラッチパッドの鍵、secret、env ファイル、`pg_dump`、手順 1 の記録を消す。投稿に使ったスクリーンショットも、写っている鍵が使い捨てでも残さない。URI の記録と保存した応答本文も secret や nsec を含むので消す

## つまずきやすい点

- **秘密の grep の準備**：ローテーションや削除の後では元の secret を取り出せない。変更の前に毎回、ダッシュボードの URI を保存しておく。記録漏れの保険として、ログに 32 文字の 16 進の語が無いことも確かめる（64 文字の 16 進は公開鍵とイベント id で埋まるので、件数を数えても役に立たない）
- **取り消しの対象**：同じ署名者に複数のセッションがあるので、署名者だけで取り消しのフォームを選ぶと別のセッションを消す。クライアントの公開鍵でも絞り、一致が 1 件であることを確かめてから押す。ダッシュボードの HTML は 1 行なので、`sed` の行範囲で節を切り出す方法は使えない
- **DB の止め方**：`docker pause` では接続が切れないので、pgo のクラッシュレポートは出ない。`docker stop` や `docker rm` で接続が切れると、クラッシュレポートに DB のパスワードが出る（`docs/design-decisions.md` の「pgo のクラッシュレポートには DB のパスワードが出うる」）
- **名前解決の失敗**：`docker stop` でリレーを止めると compose の DNS から名前が消え、再接続のたびにクラッシュレポートが出る（#46）。修正されるまでは既知の件として扱い、`docker restart` では出ないことと区別して書く
- **再起動後のログ**：本体やアクターの再起動の直後に出る `ignored: request predates this bunker instance` は、再起動前のリクエストを再実行しないための保護で、正常な動作である。バンカーの購読は送った時刻の 60 秒前以降のリクエストを求め、起動時刻の検査は重複排除より前にあるので、そのうちアクターの起動より前のリクエストをリレーが配送するたびに 1 行出る（2 台から届いた同じリクエストは 2 行になる。#54 では、2 台を使う本体のコンテナーの再起動で 24 行）
- **英語のまま出る理由**：日本語のページでも、管理 UI の外から届く理由（アカウントの一覧を得られない理由、409 の `account is already registered`、プラグインの再有効化の 503 の理由）は英語のまま出る。`docs/admin-ui.md` の「画面」に書かれた仕様で、不具合ではない
- **CSRF の拒否のログ**：別オリジンの POST を拒否するたびに、wisp が `warning Origin-host mismatch: <Host> <Origin か Referer>` の 1 行を出す。期待どおりの出力で、秘密は含まない
- **制御文字のラベル**：ラベルは `string.trim` で前後の空白を除いてから制御文字を検査するので、末尾の U+0085（Unicode の空白でもある）は除かれ、303 で登録される。拒否を確かめるときは制御文字をラベルの途中に置く
- **生の制御文字**：エージェントの環境では、ファイルに書いた `"\u0085"` が生の文字に置き換わることがあり、Bash のツールは生の制御文字を含むコマンドを受け付けない。スクリプトでは文字を符号位置から組み立てる（例は reference.md のブラウザーの節）
- **cookie のヘッダー**：Playwright の `response.headers()` は `set-cookie` を含まないので、`response.allHeaders()` で読む
- **FIFO のクライアント**：接続したままのクライアントに命令を送るとき、FIFO を `exec 3<>fifo` のように読み書き両方で開いておかないと、書き込み側が止まる
- **nostr-tools の拒否**：`BunkerSigner` は拒否を `Error` ではなく文字列で投げる。表示は `e instanceof Error ? e.message : String(e)` にする
- **本文ファイル**：エージェントの環境によってはレポートのファイルを Write で作れないことがある。その場合は `--body-file -` にヒアドキュメントで渡す
